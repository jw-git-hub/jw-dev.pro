# jw-dev.pro — правила проекта

Сайт-визитка разработчика. Статика на Astro, деплой на свой VPS за Nginx.

## Что читать перед работой

| Файл                    | Что там                                                             | Статус                                                                         |
| ----------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `docs/DESIGN-GUIDE.md`  | Визуальный язык: токены, стекло, тайминги, брейкпоинты              | **Обязателен к исполнению**                                                    |
| `docs/13-final.html`    | Макет владельца                                                     | **Только внешний вид.** Структура, тексты, цены и цифры в нём демонстрационные |
| `docs/CONTENT-CASES.md` | Схема кейса и регламент скриншотов                                  | Схема данных                                                                   |
| `docs/ARCHITECTURE.md`  | Как устроен этот репозиторий                                        | Правится на месте при изменениях                                               |
| `docs/PLAN.md`          | **План работ: 12 фаз, критерии «готово когда», что ждёт владельца** | Читать первым. Фаза закрыта — ставим галочку                                   |
| `JOURNAL.md`            | Хронология разработки                                               | Новое сверху, лимит 200 строк                                                  |

## С чего начинать сессию

Открыть `docs/PLAN.md` — раздел «Прогресс» показывает, какая фаза следующая и что
заблокировано на стороне владельца. Затем `JOURNAL.md`: последняя запись объясняет,
на чём остановились и почему приняты решения, которые видны в коде.

## Трекер владельца

Владелец следит за прогрессом в своём Obsidian:

```
/Users/jw/jw_sync_vault/📒 Obsidian/Не разобрано/Работа/Project - jw-dev.pro/Сайт jw-dev.pro/Процесс разработки сайта jw-dev.pro.md
```

Держать его в актуальном состоянии — обязанность, а не опция. Обновлять, когда
закрыта фаза, снят пункт техдолга, появился новый блокер или владелец ответил
на вопрос из «Ждёт владельца». Пересчитывать три шкалы прогресса, править дату
в шапке, переносить сделанное в «Закрыто».

Тон — человеческий и короткий: это не план, а доска «где мы сейчас». Подробности
живут в `docs/PLAN.md`, туда же уходят причины решений. Раздел «Твои задачи»
владелец правит сам — перед перезаписью читать файл и сохранять его галочки.

## Железные правила

**1. Ноль инлайна в отдаваемом HTML.** Ни `<style>`, ни `<script>` в разметке, ни атрибутов
`style=`, ни обработчиков `on*=`. Всё во внешних файлах. Без этого не работает строгий CSP.
Стережёт `tests/check-inline.mjs`.

Единственное исключение — `element.style.setProperty()` из JS для покадровых `transform`
и `opacity` в анимациях. Это CSSOM, а не инлайн в разметке.

**2. Стили — только глобальные файлы в `src/styles/`.** Блоков `<style>` внутри `.astro`
не бывает: гайд написан как глобальный CSS с конкретными именами классов, дублировать их
в скоупы бессмысленно, а из HTML заодно уходят служебные `data-astro-cid-*`.

**3. Визуальный язык не трогаем.** Расхождение с `DESIGN-GUIDE.md` — это баг, а не улучшение.

**4. Русский — источник истины.** Тексты пишутся на русском, английский переводится с него.
Ключ без пары валит сборку (`tests/check-i18n.mjs`).

**5. Цифры только измеренные.** Ни одной выдуманной метрики, ни одного отзыва, которого нет
в письменном виде. Нет измерения — поле остаётся пустым.

**6. Работает без JS.** Навигация, кейсы, статьи, журнал, переключение языка и отправка
формы обязаны работать при отключённом JavaScript.

**7. Семантика и доступность.** Один `<h1>` на страницу, уровни заголовков без пропусков,
WCAG 2.2 AA. Проверяется `html-validate` на собранном HTML.

## Команды

```
npm run dev      сервер разработки
npm run build    прод-сборка в dist/
npm run lint     ESLint + Stylelint + Prettier
npm run check    сами ворота, схема контента, переводы, покадровые свойства,
                 бюджеты слоёв, инлайн, HTML, ссылки, бюджет веса
npm run verify   браузерные ворота: доступность, работа без JS, три движка, Lighthouse
```

`npm run lint`, `npm run check` и `npm run verify` — те же ворота, что в CI.
Красное — деплоя нет.

`verify` поднимает собранный `dist` и открывает его в настоящем браузере, поэтому
идёт после `build` и требует движков: `npx playwright install chromium firefox webkit`
один раз. Минута с небольшим — почти всё это Lighthouse, который меряет каждую
страницу трижды и берёт средний результат.

## Чистый код

Один файл — одна ответственность. Функция делает одно действие, ~20 строк потолок.
Имена объясняют смысл, а не тип. Магические числа выносим в именованные константы.
Вложенность максимум 2–3 уровня. Мёртвый код удаляем, не комментируем.

Комментарий объясняет **почему**, а не **что**. «Прибавляем 78px» — мусор,
«отступ на высоту липкой шапки, иначе якорь уезжает под неё» — польза.
